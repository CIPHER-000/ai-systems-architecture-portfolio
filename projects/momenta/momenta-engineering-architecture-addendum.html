Section 1Purpose of This Addendum

The first two documents covered direction and execution. This one covers the engineering shape underneath. It explains how the AI concierge, behavioral memory, recommendation engine, and supply intelligence pipeline actually connect to each other and to Momenta's existing stack.

This is not a final production specification. It is a blueprint for how the first versions could be built and how they would evolve. It is detailed enough to show that there is a real technical plan behind the product vision, while staying readable for a non-engineering founder.

A few non-negotiables guide the architecture:

  • The LLM is not the source of truth. Momenta's approved supply layer is.
  • The system separates trusted, curated intelligence from the conversational AI surface that talks to users.
  • The architecture should start small and extend the existing stack naturally rather than introducing new infrastructure for its own sake.

Section 2High-Level Architecture Overview

At a high level, Momenta's system is made of three groups of components: a user-facing surface, a set of intelligence layers in the middle, and a supply intelligence pipeline that runs in the background.

User-facing surface

  • Next.js frontend. The web and mobile-web experience users interact with. Concierge chat, recommendations, booking flow, profile.
  • WebSockets. Used to stream concierge responses and keep conversations live.

API and orchestration

  • NestJS API. The main backend. Handles auth, session, REST and WebSocket endpoints, and routes calls to the concierge and recommendation services.
  • Concierge AI Orchestrator. A service inside the backend that coordinates the flow of a single user message: intent extraction, memory lookup, recommendation retrieval, LLM call, response streaming.

Intelligence layers

  • Recommendation Engine. Selects and ranks candidate experiences for the concierge to discuss.
  • Behavioral Memory Layer. Stores and retrieves what the system knows about each user and group.
  • Curated Supply Database. The single source of truth for approved venues and experiences.

Storage and retrieval

  • PostgreSQL. Primary relational store for users, bookings, supply, conversations, memory, and scoring.
  • pgvector. Extension inside the same Postgres instance for semantic memory and similarity search.
  • Meilisearch. Fast keyword search over supply and internal lookups.

Background processing

  • Redis + BullMQ. Job queues for the supply intelligence pipeline, embedding generation, scoring, and any other async work.
  • Workers. Independent processes that pick up jobs and write results back to Postgres.

Curation interface

  • Human Review Interface. An internal Next.js dashboard for the curation team to review, approve, or reject candidate supply.

Observability

  • Sentry / BetterStack. Error tracking, uptime, queue health, and visibility into LLM and worker failures.

The orchestrator coordinates the flow, while the recommendation engine retrieves, filters, and ranks approved supply. The LLM only sees the shortlist the recommendation engine returns, never the supply database directly.

Flow note: The orchestrator requests candidates from the recommendation engine. The recommendation engine returns the top 2–3 ranked candidates. The orchestrator then sends the shortlist and memory context to the LLM.

Section 3Core System Principle: Grounded AI

The concierge should speak fluently, but it should only recommend what the system can trust.

Generic chatbots improvise from whatever is in their training data. That is a problem for Momenta in three ways. The model can recommend places that do not exist or no longer exist. It can describe a place inaccurately. And it gives Momenta no control over the curation quality that makes the brand work.

The LLM is not the source of truth. Momenta's approved supply layer is.

Grounding the AI in Momenta's approved supply layer solves this in a few ways:

  • No hallucinated recommendations. The LLM never invents venues. It only describes candidates that the recommendation engine selected from the curated supply database.
  • Brand trust holds. Every venue users see has passed Momenta's approval workflow. The AI's job is to interpret, explain, and personalize the shortlist, not invent supply.
  • Explainable answers. Because recommendations come from structured signals (scores, tags, fit metrics), the system can explain why something was suggested instead of producing opaque output.
  • Failure mode is honest. When the system does not have a good match, the concierge says so. It does not pad the response with weaker options to look complete.
The curated layer decides what can be recommended. The LLM decides how to say it.

Section 4User-Side Concierge Flow

Walking through what happens technically when a user sends a message like "Need somewhere calm for 4 people tonight."

  1. Send. The user types in the Next.js chat surface. The frontend opens or reuses a WebSocket connection and sends the message to the NestJS API.
  2. Persist. The API records the message against the user's conversation thread in Postgres.
  3. Intent extraction. The orchestrator extracts structured intent: occasion (casual dinner), group size (4), ambience (calm), time (tonight), location (user's current city), any constraints.
  4. Memory lookup. The behavioral memory layer returns relevant context: this user's preferred ambience, typical group size, prior declines, recurring companions, dietary constraints.
  5. Candidate retrieval. The recommendation engine pulls candidate experiences from the curated supply database using hard filters first (city, availability, party size, constraints).
  6. Ranking. Candidates are re-ranked using behavioral signals, semantic similarity against past preferences (via pgvector), and supply quality scores.
  7. LLM response. The orchestrator hands the top 2-3 candidates plus their key signals to the LLM with a tightly scoped prompt. The LLM produces a short, warm response that names each candidate, explains why it fits, and offers a next step.
  8. Stream. The response streams back over the WebSocket to the chat surface.
  9. Capture signals. Any new context (preferences, constraints, declines) is written back to memory as structured fields or as a new memory event for later embedding.

Section 5Behavioral Memory Architecture

The behavioral memory layer is what lets Momenta feel like it remembers you. It has two parts.

Structured Memory

Stored in PostgreSQL as normal relational data. This is the reliable, filterable, queryable part.

Examples of what lives here:

  • Preferred ambience (intimate, lively, outdoors, lounge, etc.)
  • Typical group size and composition
  • Budget comfort range, inferred from actual bookings
  • Dietary constraints and accessibility needs
  • Preferred neighborhoods or trip patterns
  • Recurring companions and how preferences shift with them
  • Categories or descriptors the user has declined
  • Booking frequency and weekday/weekend tendencies

Structured memory is fast to query, easy to debug, and trivial for the recommendation engine to filter on.

Semantic Memory

Stored as embeddings in pgvector, inside the same Postgres instance. This is the nuanced, fuzzy part.

Examples of what gets embedded:

  • Conversation summaries
  • Past booking context and notes
  • Free-text preference statements ("we like places where you can actually hear each other")
  • Post-experience feedback ("too loud", "loved the back room", "not really our vibe")

Semantic memory captures the things that do not fit cleanly into a structured field. When the user says something like "somewhere good for catching up", the system can find the cluster of past experiences they reacted positively to in that mode, even if no single field describes it.

The two layers work together. Structured memory handles the hard filters and known preferences. Semantic memory handles tone, nuance, and pattern matching.

Section 6Recommendation Engine

The recommendation engine sits between memory and the LLM. Its job is to produce a short, high-confidence shortlist that the concierge can speak about.

Pipeline

  1. Extract intent. Occasion, group size, ambience, time, constraints, location.
  2. Apply hard filters. City, date/time availability, party size, dietary or accessibility constraints, price range.
  3. Pull candidates. Query the curated supply database for everything that survives the filters.
  4. Retrieve behavioral memory. Structured user and group preferences.
  5. Retrieve semantic matches. Use pgvector to find candidates whose descriptions or past feedback patterns line up with the user's expressed intent and history.
  6. Re-rank. Apply the scoring formula below.
  7. Return top 2-3. Not 20.
  8. LLM explanation. The orchestrator hands the shortlist plus the strongest fit signals to the LLM, which generates the response.

Scoring (conceptual)

final_score =
    supply_quality_score
  * user_preference_fit
  * group_fit
  * contextual_fit
  * feedback_confidence
  - constraint_penalties

This is conceptual, not final math. The point is that scoring is a composition of signals the system can explain, and that hard constraints (a dietary requirement, an accessibility need, an unavailable date) act as penalties or filters rather than soft suggestions.

A few principles the engine should hold:

  • Decision confidence over coverage. Two strong matches beat ten mediocre ones.
  • Honesty when there is no match. If nothing scores well, the concierge says so instead of force-fitting.
  • Freshness matters. A venue the user has just been to should drop down the list unless they specifically asked for it again.
  • Feedback closes the loop. Post-experience signals update both the user's profile and the venue's supply score.

Section 7Supply Intelligence Pipeline

This is the internal, non-user-facing side of the system. It is what keeps recommendation quality high without burning out the team.

Human review does not happen during a user's live concierge session. The supply intelligence pipeline runs asynchronously in the background, continuously discovering, enriching, and scoring potential venues or experiences. Approval happens before candidates enter the approved supply database. Once approved, they become available for real-time recommendation by the concierge.

Pipeline

  1. Discovery. Workers crawl Instagram, TikTok, Google Maps, local blogs, creator posts, and partner leads. Each candidate enters the system as a draft SupplyCandidate.
  2. Enrichment. Workers pull photos, descriptions, tags, reviews, social signals, price band, location, opening hours, and any operational details available.
  3. AI Classification. An AI step labels each candidate on ambience, uniqueness, group fit, aesthetic quality, and trust indicators. Each label is stored alongside the signals that produced it.
  4. Scoring. A Momenta Fit Score is computed from the classified signals.
  5. Review and approval. Each candidate passes through one of three approval paths (human review, AI-assisted fast-track, or AI auto-approval) depending on signal confidence and risk. See Approval Modes below.
  6. Approved Supply Database. Approved candidates move into the curated supply database and become visible to the recommendation engine. Every approval stores the mode used, confidence level, signals referenced, model version, reviewer (human or AI), and any human override.
  7. Feedback Loop. Booking outcomes and post-experience signals update the supply score over time. Venues that consistently underperform lose ranking weight.

Approval Modes

Approval is not a single step. It is a configurable workflow with three modes, applied based on candidate signals and risk profile.

  • 1. Human Review Required. The default quality gate, especially early on. Used for new host categories, premium or high-risk experiences, ambiguous quality signals, low-confidence AI scoring, safety- or brand-sensitive experiences, and first-time providers.
  • 2. AI-Assisted / Fast-Track Approval. Used when signals are strong but still worth a quick human pass. Strong candidate signals, consistent positive reviews, clear fit with Momenta's rules, strong visual quality, and reliable metadata. AI prepares the recommendation; humans batch-confirm rather than reviewing from scratch.
  • 3. AI Auto-Approval. Used later, once the system has a track record. Reserved for very high-confidence candidates, repeat hosts, existing partners adding new experiences, low-risk categories, and candidates that match patterns of historically successful supply.

The point is that AI handles more of the approval burden over time while humans stay focused on edge cases, brand-sensitive decisions, and quality control. Auto-approved candidates are still auditable, and periodic human audits should sample them to protect quality.

A few engineering rules around this:

  • Asynchronous. Approval runs in the background. The user-facing concierge never waits for it.
  • Explainable. Every AI approval decision must point to the signals and thresholds that produced it.
  • Configurable rules. Approval thresholds, mode routing, and category-specific overrides are stored as configuration, not hard-coded.
  • Auditable. Every decision is logged with mode, confidence, signals used, model version, timestamp, reviewer, and override status.
  • Reversible. A human can override or revoke any AI approval at any time, and the override is recorded against the candidate.

Why BullMQ and Redis matter here

The supply pipeline is naturally asynchronous and bursty. BullMQ on top of Redis is the right tool for this:

  • Background jobs. Discovery, enrichment, scoring, and embedding generation all run off the user-facing request path.
  • Retries. Scrapes fail. Job retries with backoff are built in.
  • Scheduled runs. Recurring discovery on a daily or weekly cadence is straightforward.
  • Backpressure. The user-facing app stays responsive even when the pipeline is processing thousands of candidates.

The existing stack already includes BullMQ, so this is a natural extension rather than new infrastructure.

Section 9AI Orchestration Layer

The orchestrator is a small service inside the NestJS backend. It is the place where intent, memory, retrieval, and the LLM get composed into a single response.

Responsibilities

  • Route incoming user messages to the right handler.
  • Extract intent from each message and update conversation state.
  • Decide when the system has enough context to recommend, and when one short clarifying question is needed.
  • Fetch the relevant slice of behavioral memory.
  • Call the recommendation engine and receive the shortlist.
  • Build the LLM prompt with grounded context: the shortlist, the relevant memory, the conversation so far.
  • Enforce grounding rules before returning anything to the user.
  • Stream the response back through WebSockets.
  • Log signals from the exchange back into memory.

Guardrails

  • No unsupported venue claims. The LLM is given a fixed set of candidates and may not reference any other venue by name.
  • No invented availability. Availability statements come from structured data, not the LLM.
  • Use internal signals for the "why". Explanations are grounded in scored signals (ambience, group fit, uniqueness) rather than improvised text.
  • Graceful fallback. When confidence is low, the concierge says "I don't have a great match for that this weekend, want me to look at next week or something else?" rather than padding the response.
  • Human handoff. Edge cases (large groups, sensitive occasions, partner-only experiences) can route to a human concierge instead of forcing the AI to handle them.
This is the difference between "an LLM in the product" and "an LLM as the product." The LLM is one component among several. It does not get to override the curation layer.

Section 10Software System Fit With Existing Stack

The architecture lines up cleanly with what is already in place.

  • Next.js. User-facing concierge UI, recommendation cards, booking flow, and the internal review dashboard. One framework, two surfaces (consumer and internal).
  • NestJS. REST and WebSocket API, auth and session, concierge orchestration endpoints, recommendation and supply intelligence services. The orchestrator lives here as a module.
  • PostgreSQL. Core relational data: users, groups, bookings, supply, conversations, memory, scoring, decisions. Single source of truth.
  • pgvector. Inside the same Postgres instance. Semantic memory, similarity search over user and group context, supply description matching. Avoids the overhead of a separate vector database.
  • Redis + BullMQ. Async jobs: supply scraping, enrichment, embedding generation, scoring, memory summarization, scheduled discovery runs.
  • Meilisearch. Fast keyword search over supply and internal lookups. Useful both for the curation team and for any user-facing browse surfaces later.
  • WebSockets. Streaming concierge responses, live conversation experience, and shared group planning threads when those arrive.
  • Sentry / BetterStack. Error tracking, uptime, queue health, LLM call visibility. Critical when an AI system is in the path.
  • Docker. Local development, predictable deploys, easy worker scaling.
  • Cloudflare. CDN and edge protection for the consumer surface.

The point is that nothing in the architecture requires a new infrastructure category. pgvector and additional BullMQ workers extend what is already there.

Section 11MVP Technical Scope

Sequenced, not dated.

Phase 1

  • Chat UI in the Next.js app.
  • Concierge endpoint and WebSocket gateway in NestJS.
  • Basic intent extraction.
  • Basic recommendation engine that retrieves from a manually-populated curated supply table.
  • Basic ranking using hard filters and supply quality.
  • Conversation persistence.
  • Lightweight post-experience feedback capture.

Phase 2

  • Structured behavioral memory tables and update logic.
  • pgvector enabled. Embeddings generated for conversation summaries, memory events, and experience descriptions.
  • Memory-aware recommendation re-ranking.
  • Post-experience feedback loop wired into both user profile and supply score.

Phase 3

  • Supply intelligence workers: discovery, enrichment, AI classification, scoring.
  • Human review dashboard inside the same Next.js app.
  • Feedback loop from bookings into supply scores.

Phase 4

  • Group profiles and group preferences.
  • Shared concierge threads for group planning.
  • Deeper personalization across recurring groups.

Section 12Risks and Design Decisions

Risk Mitigation
AI hallucination The LLM only ever speaks about candidates the system already approved. Grounding is enforced at the orchestrator level.
Generic AI tone Treat the concierge's voice as a product surface. Prompt design and tone testing are first-class work, not a side task.
Poor supply quality Human review on top of AI scoring. The curation team is the final gate, with AI-assisted and auto-approval modes introduced gradually as confidence is earned.
Over-automation of curation Approval is phased across three modes (human, AI-assisted, AI auto), gated by category, risk, and confidence thresholds. Auto-approved candidates remain auditable, and humans can override at any time.
Live approval bottleneck Supply intelligence runs asynchronously. The user-facing concierge only ever recommends from already-approved supply, so it never waits on a reviewer.
Opaque AI decisions Every approval stores the signals, confidence, model version, and approval mode that produced it. Periodic human audits sample auto-approved candidates to protect quality.
Privacy and social data concerns Group and companion data is opt-in. Store the minimum needed for useful recommendations.
Onboarding friction Short onboarding plus learning-by-observation. Memory builds from behavior, not surveys.
Weak feedback loops Post-experience feedback is one tap plus an optional sentence, wired into both user memory and supply scoring.
One person owning too many disciplines Clear ownership across AI/backend, frontend/mobile, and UX/UI, as covered in the proposal's team structure section.

Section 14Closing

The architecture can start simple. The existing stack is a strong foundation, and the pieces that need to be added (pgvector, additional BullMQ workers, the orchestrator module) extend what is already there rather than replacing it.

The principle that ties everything together is grounding. The AI stays useful because it stays inside Momenta's curated supply and behavioral memory. The curation layer keeps brand trust intact. The feedback loops make both layers sharper over time.

If those three things hold (grounded AI, curated supply, working feedback loops), the rest is engineering work that can be sequenced sensibly without overbuilding.
